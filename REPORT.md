# Design write-up

## 1. Architecture

One Node/TypeScript process, four modules with hard boundaries, and one seam I care about more than the rest.

**Surface** (`src/surface`) is the seam. Everything above it sees only `Observation`s (a list of controls with a role, an accessible name, the frame they live in, the label cell to their left, and for table cells the column header and the other cells in the row) and `TargetSpec`s (how to find a control again). Nothing above it imports Playwright. The one concrete surface walks every frame of a page, indexes controls without using ids or test ids, and stashes live element handles so a matched record can still be clicked. Perception is text and structure, not pixels: cheaper, and it survives the framesets and table layouts in the target environment. I wrote the target app to be hostile on purpose (framesets, `<font>`, `txt1`/`sel1` input names, native `confirm()` on posting) so the locator story would be tested against the real shape of the problem rather than a clean demo site.

**Discovery** (`src/discovery`) is the observe, decide, act loop with the model in it exactly once per action. The model gets a compact text rendering of the observation and a small tool set (`click`, `type`, `select`, `extract`, `declare_outcome`, `done`, `stuck`). Every tool call passes through the same policy engine replay uses before it touches the surface; a blocked action is fed back to the model as a result, not silently dropped. A recorder re-expresses each action as a step. The model transcript is evidence, not the artifact.

**Replay** (`src/replay`) is the production path. No model. Per step: detect known conditions, resolve the target through its fallback ladder, authorize, act, verify the post-condition. It returns a four-way result (`success`, `outcome`, `failed`, `escalated`) with a per-step report, drift warnings, recoveries and interventions.

**Policy and handoff** (`src/policy`, `src/handoff`) are shared by both loops. The session controller owns a lease on the live browser; automation asserts it holds the lease before every action.

Trade-offs I made deliberately: a single process rather than services, because the brief evaluates abstractions and the queueing story adds nothing to them; file-backed artifacts rather than a database, because a capability is a reviewable unit and git diffs are the review tool; OpenAI tool calling with `gpt-4.1` at temperature 0 with `tool_choice: required`, because structured actions are the point and a chatty model is a liability here. The model boundary is an interface (`LLM`) with a scripted implementation, so the whole pipeline, including tests and an offline evidence suite, runs without a key.

## 2. Artifact schema

A capability (`src/artifact/schema.ts`, zod) is a contract first and a step list second. The top of the file is what an agent or reviewer needs: `inputs` (typed, with `pattern`, `enum`, `required` and a `sensitivity` of `none | pii | secret`), `outputs` (typed, each pointing at the extract step that produces it), `outcomes` (the business results this flow can legitimately end in), `policy` (allowlisted origins and routes derived from the routes actually visited during discovery, plus `maxRisk`), `success` (a checkpoint), and `provenance` (model, run id, goal, tenant, how many times a human intervened during recording). Because inputs and outputs are already JSON-schema-shaped, the catalog turns a capability into a function-calling tool definition with no extra metadata.

Steps carry a `TargetSpec`, a `ValueRef`, a `risk` and an `expect`. Three decisions in there matter:

- **Values are references, never literals that were typed.** A typed value that equals a declared input is recorded as `{kind: "param", name}`; credentials are `{kind: "secret", ref: ENV_NAME}` and are filled from the environment at run time. The model never sees a secret value (it types by reference), and no secret or pii value can be serialized. As a second line of defense the recorder substitutes `{memberId}` for the input's value anywhere it leaked into prose, and the whole artifact passes the redactor before it is saved.
- **Targets are a ladder, not a selector.** Ordered strategies, each with a name that says what it relies on: `role`+name, `anchor` (the label cell to the left or above, which is how a person reads a table form), `grid` (row key + column header, so "the Current Balance of the Share Savings row" survives a different member's data), `text` (labels only, never data values), `attr` (tag + `name`/`type`, ugly but vendors rarely rename `txt1`), and a `css` path last. A `fingerprint` (tag, role, attribute name, type, label) travels with the target so a fallback hit can be checked against what was recorded. `description` is a sentence for the reviewer.
- **Post-conditions are derived, not invented.** After each action the recorder diffs frame URLs; a frame that navigated becomes `expect: {urlMatches: "/t/alpha/members/:id"}` with numeric segments canonicalized. The success condition is the final route plus an exact piece of on-screen text the model had to name (`"MEMBER DETAIL"`, never a number).

Things that are *not* per-capability live in an **app profile** (`apps/legacycore-teller.json`), one per vendor product: the conditions every flow must survive (session expiry, interstitial, app error, not found, permission denied, validation error) with their detectors and recoveries, the secret references, the regex that marks a control as committing, and the tenants. Copying "session expired" into every artifact would be the wrong shape. Outcomes discovered during a run (`declare_outcome`) still land in the artifact so nothing the model saw is lost.

Versioning is `version` plus `status: draft | approved | deprecated`. A draft replays, but an irreversible step in a draft always escalates. Tenant overrides are sparse patches per step id inside the same artifact, so one recording is one file with a small delta per institution.

## 3. Determinism & error handling

Determinism comes from removing every decision from the replay path: which control (the ladder plus fingerprint), what value (the reference), when to move on (quiescence plus the checkpoint), and what an unexpected screen means (the condition vocabulary). The surface's `settle()` waits until no navigation request is in flight and every frame's document is complete, which handles frameset navigations that Playwright's page-level load events miss; the engine then polls the step's checkpoint up to a timeout and stops polling early if a known condition appears instead.

Runtime conditions are classified in exactly three kinds, and each kind maps to exactly one behavior:

| kind | meaning | engine does | shows up as |
|---|---|---|---|
| business | a legitimate answer ("No record found", "Insufficient privileges", a validation message) | stop, capture the app's own message | `status: "outcome"`, code + message + step |
| recoverable | interstitial, session expiry, slow host, unexpected dialog | run the recovery (dismiss, re-auth + restart, wait longer, dismiss), then retry or re-verify; give up after two recurrences | `recoveries[]` on a result that is otherwise success |
| hard | app error page, control not found after retries, checkpoint failed, output unparseable | stop with a failure bundle (screenshot + DOM of every frame) and expected vs observed | `status: "failed"` with `failure.code`, step, expected, observed, evidence paths |

Detection runs before every step (except `navigate`, which leaves the current screen anyway) and again when a post-condition fails, which is where business outcomes usually surface (submit, then "No record found"). One subtlety: a recoverable condition that appears *after* an action (tenant beta's post-login notice) is cleared and then the post-condition is re-checked rather than redoing the click, so the engine does not submit a form twice. Input validation against the contract happens before the browser is touched (`INVALID_INPUT`), and the output contract is enforced at the end (`OUTPUT_MISSING`).

Drift is secondary here and is treated as a signal rather than a failure. When a fallback rung matches, the step still runs and the result carries a `drift` warning with the strategy that worked and a fresh `TargetSpec` rebuilt from the control as it looked this time. Weak rungs (`css`, attribute-only) are not allowed to pick a differently labelled control: a structural match must agree with the recorded label, or be the only control of its role in the frame. The false positive I was guarding against is concrete: the css path recorded for "Member Inquiry" on tenant alpha lands on "Teller Drawer" on tenant beta.

## 4. Heterogeneity & multi-tenant

**Surface abstraction.** The recorded flow never mentions DOM. A step says "the textbox to the right of *Member Number*, in the frame whose route is `/members`", and the fingerprint says what kind of control that was. A desktop surface produces the same `ObservedElement` records from the OS accessibility tree (UIA / AX / AT-SPI all expose role, name, bounding box, and parent/sibling structure; `anchor` becomes "the static text left of the control", `grid` becomes the row/column of a data grid, `frame` becomes the window or pane). Because `resolveTarget` is a pure function over those records, the ladder, the fingerprint check and the drift signal carry over untouched; only `observe()` and `act()` are reimplemented. A screenshot-plus-coordinates surface fits the same interface with `bbox` as the primary key and OCR text as `name`, which is why `bbox` is already in the record even though the web surface does not need it. The seam between "how we perceive and act" and "the recorded flow" is exactly the `Surface` interface: the artifact is on one side, Playwright is on the other, and `locator.ts` is the only code that has to understand both.

**Multi-tenant reuse.** Hundreds of institutions on the same vendor product differ in branding, labels, frame names, menu order and interstitials, not in structure. The design handles that in layers. The ladder absorbs the small stuff for free (the drift report from tenant beta shows `Operator ID` for `User ID` and `Log In` for `Sign On` resolving through the `attr` rung, `Ledger Balance` for `Current Balance` resolving through `anchor`). What the ladder cannot absorb escalates to a person on the live session. Then `learn-overrides` turns that one run into a **tenant override**: every drift warning contributes the rebuilt target as that tenant's primary, and a step the operator performed by hand contributes a target derived from their recorded click ("Customer Lookup" for "Member Inquiry"). The override is written as a new draft version for review; the base recording is untouched, and other tenants are unaffected. Evidence runs 10 through 12 show the full loop: recorded on alpha, replayed on beta with six drift warnings, one recovery and one handoff, then replayed on beta again with zero drift and no intervention.

Drift detection at scale is the same signal aggregated: per tenant and version, the rate of fallback hits per step is a canary for a vendor upgrade, and the rebuilt targets are the raw material for the next override proposal. I did not build the aggregation; the result contract carries everything it would need.

## 5. Escalation & handoff

"Stuck" is decided by code, not by feel: a control that no rung can locate after retries, a recoverable condition that recurs after its recovery, an irreversible step the run is not authorized for, a checkpoint that fails without a recognizable condition, or, in discovery, the model calling `stuck`. Each raises an `InterventionRequest` carrying the run, phase, capability, goal, step, cause (the outcome code and message), current URL, a screenshot, a text summary of the screen, and suggested actions.

The control model is a **lease on the session** (`src/handoff/control.ts`). Automation holds it by default and asserts it before every action. Raising a request parks automation in `requestIntervention()` and notifies operators. A named operator calls `takeControl()`: the lease flips to them, and the surface starts capturing their input (clicks, changes, submits, navigations, with password values redacted) on the same live page, same cookies, same frame tree. They act in the automation's own browser window. `handBack()` carries a decision: *resume* (retry the step), *skip_step* (they did it), or *abort*. The captured actions ride along with the resolution into the run's evidence and, on another tenant, into an override proposal. If nobody answers within the timeout the request expires into an abort and the run ends `escalated`. Two humans cannot hold the session at once, a hand-back from someone who does not hold it is refused, and only one request can be pending.

One detail worth calling out: a native `confirm()` cannot be shown to a remote operator, so whoever holds the session answers it in advance. Automation answers via the step's recorded `dialog` field; a human answers by pressing OK or Cancel in the console before acting, and anything unanswered is dismissed. That keeps "who is in control" true for modal dialogs too, rather than letting an unattended accept slip through.

What is mocked and what is real: the mechanism and the transfer model are real and unit-tested; the operator surface is deliberately bare. There is a small HTTP console (list requests, take control, hand back) meant to be used with `--headed`, and a scripted operator for headless evidence that drives the same page through plain Playwright calls, exactly what a person does with a mouse. A real console would add a live view of the session and identity; it would still call the same two functions.

## 6. Safety

The guardrail model has three parts, all enforced before an action reaches the surface, in both loops.

**Allowlist.** Origins, routes and action kinds. During discovery the allowlist is the entry origin; the recorder writes the routes actually visited (canonicalized) into the artifact, so a replay is confined to the paths the recording used. Links are checked by their resolved `href` before being clicked, so a control that would leave the allowlist is refused even though it lives inside an allowed page.

**Risk classes.** `safe` (typing, reading, navigating within the allowlist), `reversible` (submits that move through a flow: search, continue, back), `irreversible` (a control matching the product's committing pattern such as Confirm or Post, or accepting a native confirm dialog). Irreversible actions need two independent consents in discovery (the run started with `--allow-irreversible` *and* the model set `confirmIrreversible: true` on that call) and two in replay (an `approved` artifact *and* `confirm: true` from the caller). Anything short of that escalates to a person rather than proceeding, and the person can perform the commit and hand back with *skip_step*. Native dialogs are dismissed unless the step recorded that accepting one is part of the flow; an unexpected dialog is logged as a recovery and never accepted by default.

**Data.** Secrets are referenced by environment variable name in artifacts and are typed by reference by the model. Every string that reaches a log, an evidence file or a saved artifact passes the redactor, which masks secret values (longest first, so a password containing the username is masked whole), pii-marked input values (keeping two characters so runs can be correlated), and anything shaped like an SSN or card number. Outputs marked pii are masked in logs but returned to the caller in full, since the caller asked for them and owns their handling.

Limits, stated plainly: risk classification is a regex over control names plus the dialog signal, which is right for this product and will need a per-app list (and probably a route pattern) elsewhere; the redactor is value-based, so a sensitive value the system was never told about (a name rendered on screen) is only caught if it matches a shape; screenshots are not redacted, so the evidence directory must be treated as sensitive; and the allowlist is enforced at the action layer, not the network layer, so a page that fetches out of band is not stopped by it.

## 7. Cuts

### Out of scope

Left out on purpose: a real operator console with a live session view; desktop and screenshot surfaces (interface and seam only); a stability score from N replays; bounded LLM recovery of a single failed step; queueing, workers, tenancy plumbing; a store beyond JSON files; visual fallbacks on the ladder. The scripted decider is not a product feature, it is the way the pipeline runs without a key and the way the end-to-end tests stay cheap.

### Known limitations

Known rough edges: `anchor` picks the nearest label cell, which on a dense grid can be the previous data cell rather than the header (the `grid` rung exists for that reason, and `learn-overrides` repairs the rest); post-conditions are route based, so a step whose only effect is client side records no checkpoint; re-auth restarts the whole capability rather than resuming at the failed step, which is safe but slow for long flows.

Next, in order: multi-run stability and an approval workflow keyed on it (draft, approved, deprecated already exist in the schema); a single-step assisted fallback where a failed rung asks the model to pick the control from the current observation under the same policy, recorded as evidence and as an override proposal; drift aggregation per tenant and version; a desktop surface over UIA to prove the seam with a second implementation; and recording per-step visible-text checkpoints during discovery so success is not only route based.
